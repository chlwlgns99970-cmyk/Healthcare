- 원본: `data-source/kfind/kfind-food-db-2026-08-28.xlsx`, `음식(19,617건)` 시트. SHA-256 `1EF3551F9A1D0EE87891D6306FA22BBD6A7FFCC90F2C70A4A184DBFE3FCE6EA6`.
- 가져오기: `tools/import_kfind_foods.py`는 원본 `영양성분함량기준량`(Q열)의 수치와 `g`/`ml`를 그대로 `food_items.csv`의 `referenceAmount`/`unit`에 기록한다. `에너지(kcal)`(R열)도 원본 값을 사용한다. 변환 과정에 ml→g 환산은 없다.
- `음식(19,617건)!A18568`의 `D401-007450000-0001`/`김밥_참치`: Q열 `100ml`, `식품중량` EY열 `400ml`, R열 `128 kcal`. 앱 CSV도 `100,ml,128`이다.

따라서 `100ml` 노출은 가져오기 단위 오류가 아니라 원본에 있는 기준량을 앱이 그대로 보여준 결과다. 다만 고형 음식의 부피 기준을 일반 사용자의 섭취량과 연결할 근거가 없어 기본 기록 선택으로 두기 어렵다. 동일 음식명 사이에서도 ml와 g의 kcal가 다르므로, 수치만 보고 서로 교체하거나 임의 밀도를 적용하면 안 된다.

## 범위와 조치

파생 CSV 전체 19,617개 중 `밥류` 424개, 그중 ml 기준 297개다. 이름에 `김밥`이 포함된 45개 중 ml 기준은 27개다. `김밥_참치` 5개 중 2개는 g, 3개는 ml 기준이다. 명백한 액체·반액체 및 혼합 범주를 제외한 고형 범주의 ml 기준은 2,382개다. 원본 엑셀·음식명·단위·영양 수치·DB 스키마는 변경하지 않았다. 파생 CSV의 검색용 정규화 필드만 NFKC 규칙으로 다시 생성했고, 새 번들 ID로 기존 설치의 검색 인덱스가 갱신되게 했다.

- 검색에서는 K-FIND 고형 범주의 ml 기준 후보를 적합한 기준 단위 후보 뒤에 배치한다.
- 해당 ml 후보는 `기준량 정보 확인 필요`로 표시하고 바로 기록 선택을 막는다. g 기준 후보 또는 직접 입력으로 이어진다. 이 항목의 원본 단위·kcal를 사용자 분량이나 g당 kcal처럼 보여주지 않는다.
- 다른 검증 음식 자동 매칭과 대체 음식에서도 이 모호한 후보를 제외한다.
- 검색어는 NFKC, 대소문자, 공백·구두점 정규화를 적용한다. 원본명 `김밥_참치`를 바꾸지 않고 `참치김밥` → `김밥참치`, `계란` ↔ `달걀`, `흰밥` → `쌀밥`, `흰우유` → `우유`를 검색 별칭으로만 추가한다. 띄어쓰기 차이인 `닭가슴살`/`닭 가슴살`은 정규화로 처리한다. 결과가 없으면 짧은 이름 재검색 및 직접 입력을 안내한다.

고형 범주의 ml 기준이 원본에서 잘못된 값인지, 혹은 별도 측정 규약을 의미하는지는 이 검토만으로 판정하지 않았다. 2,382개를 g로 변환하거나 kcal를 재계산하지 않았으며, 출처의 정의를 추가 확인할 때까지 `DATA_REVIEW_REQUIRED`로 관리한다. 액체·반액체 및 혼합 범주의 ml 값은 일괄 차단하지 않았으므로, 개별 음식 특성에 따른 후속 감사를 권장한다.

## 자동 품질 검사

`tools/check_food_data_quality.py`를 실행했다. 기준량 0 이하, kcal 음수·비유한값, 음식명/정규화명 공백, 출처 코드별 단위 충돌, 중복 ID, 추천 식단 재료의 단위 불일치는 모두 0개였다. 액체·혼합 범주의 단위 누락도 0개였다. 정규화명이 같은 키는 2,161개(관련 행 6,802개)이며, 원본에 같은 음식명의 별도 출처·측정값이 있는 정상 후보도 포함된다. 이름 중복을 임의 병합하지 않았다.

생활 단위 환산 근거는 CSV에 별도 필드가 없어 이 스크립트로 전수 판정할 수 없다. 기존 `PortionGuide`의 명시된 출처와 단위 일치 테스트를 별도로 유지한다. 추정치를 공식 제공량으로 격상하지 않았다.
