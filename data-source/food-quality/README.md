# Linked food evidence

`tools/extract_food_identity_fields.py` reads every original column and its hidden-column metadata, restoring exact K-FIND food codes, detailed classifications, manufacturer/distributor fields, package content, intake references, product-report numbers and upstream attribution. Both K-FIND importers invoke it. Original workbook SHA-256 and the bundled identity set validate cached extraction.

`tools/generate_food_metadata.py` joins that source sidecar, reviewed public recipe facts and exact official franchise evidence into `fooddata/food_metadata.csv`. Runtime lookup uses stable food/menu IDs, outside Room v8. Existing nutrition, servings, historic records and user preferences are preserved. Re-run with `--check` to verify identical generated bytes.

Full ingredient declarations, partial descriptions/reference recipes, declared allergens and cross-contact allergens remain separate. A reference recipe cannot certify another restaurant's recipe or allergen absence. Source classifications are preserved as classifications; they do not automatically establish a dish's composition. Conflicting identities are reported, not merged or averaged.

Historical recommendation tags remain in their original assets/audit, but the old `COMPLETE` flags often cite only a food name and nutrition identifier. Runtime confirmed warnings now require exact ingredient/label evidence from the metadata sidecar. Unverified historical tags cannot confirm containment or absence; unresolved foods retain a configured user's decision-point caution.

Quality counts distinguish some verified ingredients from complete declarations, and positive allergen evidence from a complete label. Every new evidence row retains the original URL/reference, checked date, source date and parser version. Menu-only entries have no manufactured nutrition value.

The K-FIND originals have no ingredient/allergen columns. The official C002 product-report ingredient API supplies those fields but requires a service key. Public domestic-food search was also checked with exact report numbers and a normal session; its AJAX response returned HTML rather than product JSON. No unverified product ingredients were imported from that response.

Final results are in `final-report.md`, `food-quality-audit.json`, `linked-quality-summary.json` and `final-validation.json`. The frozen `quality-baseline.json` preserves the captured task baseline and source-asset hashes so later clean builds do not silently report a zero baseline. The original name/tag-only recommendation count (51) is distinct from source-verified components (19 before, 151 after); complete ingredient declarations remain zero.

Run `tools/generate_food_metadata.py` and then `tools/generate_linked_quality_summary.py` to reproduce assets and summaries from the reviewed inputs. `tools/generate_food_metadata.py --check` verifies metadata and manifest bytes without modifying them. Serving coverage in the final report uses the actual Kotlin `FoodAmountPolicy` audit; the older `householdUnitEvidence` metric is only a text-evidence diagnostic. Samsung logs, targeted Unit XML, all-identity serving audit and pre/post QA preservation proof remain under `app/build/data-quality-qa/`.
